# Phase 4 part 1: reply proposals — design input

**Direction:** keep proposals as quiet, positional study annotations within the existing thread. Reuse the explorer and shared Button/Card language; add no new severity colours, card-within-card frame, or analysis-style visual emphasis. A proposal records what a reader would play, not whether it is good.

## Recommended presentation

- **Reply composer — “Propose this move”**: a compact secondary `Button` in the reply form, adjacent to (but visually subordinate to) Reply. It opens an inline proposal area, not a modal, so the position remains visible. If the post has one attached position, select it implicitly; with multiple positions, show a labelled position selector (e.g. “Position 1 · 5-point match · 3–2 · 6-4 to play”) before the relevant controls. Keep the existing reply text field and proposal draft in one form submission, with a clear “Remove proposal” action before submit. For checker positions, reuse `CheckerMoveExplorer` and add an explicit “Use this play” action once a legal sequence is complete; show the selected notation as mono (e.g. `24/18 13/9*`). For cube positions, show app-worded action buttons—No Double, Double, Too good, Take, Pass—as mutually exclusive secondary buttons, with the selected option visibly outlined/washed using existing tokens, never severity colours. Include the opponent’s half as quiet supporting text where the choice is a paired cube action (e.g. Double · opponent take), consistent with `BoardPanel.styles.ts` / `MoveDelta.styles.ts`.
- **Proposal chips in replies**: place a compact, neutral outlined chip on its own wrapped line after the reply body, labelled with its position and proposal. Checker notation is mono; cube action is sans. Example: `Position 1 · 24/18 13/9*` or `Position 2 · Double · opponent take`. Make the full chip a button/link only if it has a defined action (recommended: jump/scroll to the associated position and open its tally); otherwise render a non-interactive chip, not a faux button. Multiple proposals wrap naturally. Do not use Best/Error/Blunder badges or colours: no engine verdict exists for a reader’s suggestion.
- **Position tally**: directly below the board/explorer and existing analysis, add a native disclosure with summary text exactly `Show proposals (n)`. Use a hairline top border and the same inset as the caption/analysis section, not another nested Card. Keep it closed initially. When opened, group proposals by identical position-specific play/action; show the candidate chip/notation and a right-aligned tabular count (number of replies proposing it). This keeps the position as the organizing context, avoids a long voter list, and makes the tally scannable. Use neutral ink and surface/sunken tokens; counts are not severity or equity.

## Responsive and accessible behavior

- At narrow widths, composer controls and proposal chips wrap; no min-width or horizontal-scroll requirement. Keep labels and actions in normal flow, with the board scaling as it does now. Avoid a three-column cube-action layout if labels wrap; use wrapping buttons or a single-column stack at phone width. Keep counts aligned where space permits, then allow a clean second line rather than clipping.
- Use the shared `Button` (`secondary`, `compact` for inline/card controls) and its built-in focus ring; selected cube action must expose `aria-pressed`, not just a visual state. Label position selection and controls explicitly. Preserve `CheckerMoveExplorer`’s keyboard-accessible point controls and `aria-live` status; do not use its current intermediate hop notation as a completed proposal until the move is legal/complete.
- Disclosure should be semantic `<details>/<summary>` or an equivalent button with `aria-expanded` and `aria-controls`. Keep “Show proposals (n)” as the accessible name and announce changed count when the view updates. Render empty state intentionally if zero proposals: ideally no disclosure at all when there is no tally, unless product wants a visible “No proposals yet.”
- Ensure proposal chip text is distinguishable without colour, counts use tabular numerals, and focus is plainly visible in both themes. Do not set `text-ink-faint` on a sunken surface; the design system notes its contrast limit.

## Component boundaries and suggested props

Keep these as forum-scoped components; do not change the shared board/explorer’s general purpose merely for this feature. A local implementation can begin with view-model props and callback boundaries, with its data adapter deferred to part 2.

- **`ReplyComposer`** (`app/forum/[id]/ReplyComposer.tsx`): owns reply body and the draft proposal; submits both as one user intent. Add `positions: ProposalPositionOption[]` (stable position id, display caption, kind, decoded checker position/dice/cube as needed) and a callback such as `onSubmit({ body, proposal? })`. The current `postId`/`canWrite` remain page-level inputs. Do not let board decoding or proposal display text become database persistence logic.
- **`ProposalDraft`** (private to composer unless independently reused): props `position`, `onChange(proposal | null)`, `value`; renders a checker move picker or cube action picker by position kind. Extend `CheckerMoveExplorer` only with an opt-in completion callback / action slot if this can preserve its existing explorer behavior; otherwise wrap it locally rather than adding forum-specific semantics to the shared component.
- **`ReplyProposalChip`** (shared leaf if both draft confirmation and saved replies use it): props `{ positionLabel, kind, notation?, cubeAction?, opponentAction?, onActivate? }`. Render notation and action as text; do not infer tier/equity. If it is an interactive jump target, provide a button/link name that includes the position and action, and ensure its target is stable.
- **`PositionProposalTally`** (under each attached position in `app/forum/[id]/page.tsx`): props `{ positionId, proposals: Array<{ key, label, kind, count }>, onActivateProposal? }`. It owns disclosure and grouped candidate counts, not query/fetch/persistence. Keep its grouping input precomputed, rather than teaching the view component how replies are stored.
- **Styles**: add a colocated `[component].styles.ts` for any promoted reusable component and keep route-only composition in `forum.styles.ts`. Follow `export const style = { ... } as const`, `clsx` for conditional entries, design tokens only, and shared primitives first. Reuse `Button`; avoid introducing global styles or a new chip primitive until there are multiple independent consumers.

## Existing surface reviewed

- Forum positions render a checker position through `CheckerMoveExplorer` and cube positions through plain `Board`; caption/origin metadata sits above, and analysis below (`app/forum/[id]/page.tsx:96-131`). Replies and composer share a card; the composer is currently a textarea, right-aligned primary Reply button, and error (`app/forum/[id]/page.tsx:135-156`, `app/forum/[id]/ReplyComposer.tsx:35-52`). This gives a natural inline proposal area and per-position tally location.
- Explorer is an interactive board with legal-hop handling, notation/status, and compact controls (`app/components/match-analysis/CheckerMoveExplorer.tsx:35-57,119-143,178-229`); its current public props do not expose a committed move callback (`:35-43`). Board already supplies interaction and accessible labels (`app/components/match-analysis/Board.tsx:243-283`).
- Buttons offer the established primary/secondary/quiet variants and compact size (`app/components/ui/Button.tsx:7-18`, `Button.styles.ts:7-20`). The forum’s existing position and analysis sections use inset hairlines and no extra frame (`app/forum/forum.styles.ts:33-47,63-72`).
- Style rules: shared components and design tokens, not inline classes; chip/badge patterns exist, but severity helpers are reserved for actual severity (`docs/design-system.md:180-201,203-246`).

## Decisions the implementation plan must state

1. **Proposal cardinality:** can a reply carry one proposal total, or one per attached position? Recommended default: at most one proposal per reply, attached to one selected position; this keeps the composer understandable and makes `n` a count of proposing replies. If multiple proposals per reply are needed, state whether identical proposals from that reply count once or more than once.
2. **Cube action semantics:** define which action choices are valid for each cube-position context (pre-double vs offered double/take-pass), whether Take and Pass are both available in a reply, and how the opponent’s response is represented. Show only domain-valid choices; the six labels must not imply impossible options.
3. **“Use this play” completion:** agree when the checker sequence becomes a proposal (all legal dice used, or a legal partial sequence is permitted), and whether user must confirm it. Recommended: enable explicit confirmation only for a complete legal move, retaining reset/undo until confirmed.
4. **Tally grouping and interaction:** confirm grouping key/label and whether tapping a tally entry or reply chip navigates/highlights the board. Recommended: one grouped candidate row with reply count; no author/voter list; activate to focus that position/proposal only if it can be implemented accessibly and reliably.
5. **Empty/loading/error states and edit lifecycle:** decide whether zero-count disclosure is hidden, what part 1 shows before part 2 supplies data, and whether editing a reply can replace/remove its proposal. Part 1 must not present hard-coded/fake counts or imply persistence that does not exist.
