# Raw-field inventory re-verification — against fresh live Galaxy data

Prompted by three real cases this session where a field's assumed meaning/location was wrong (`final.gnubgid` vs `source_position.formatted_value`; `cube_analysis.cube_level` vs the actual cube value; `game_started`'s dice data wrongly declared absent) — treated as a systematic risk, not three isolated incidents. This pass re-verifies the 2026-10-01 raw-field audit's (`reports/2026-10-01-decision-raw-field-audit.md`) inventory against **fresh data**, not against anything already concluded.

## Recommended actions

Everything below surfaced during a field-by-field walkthrough of this report's findings. Nothing has been implemented — this is the consolidated action list, not a status update. Each item needs its own propose-then-implement pass (same discipline as Steps 3-5 of the raw-field audit implementation), not a single bundled change.

**1. Drop `isBlunder`.** Confirmed 100% redundant with `errorSeverity === 'BLUNDER'` — 0 mismatches across 371 real rows checked. Pure function of an existing column. Before dropping: check real usage across the codebase (not done yet — this session only confirmed the redundancy, not that it's safe to remove).

**2. Drop `cubeDetail` and `detail`; add `cubeActionPlayed`/`cubeActionBest`; rename `notationPlayed`/`notationBest` → `movePlayed`/`moveBest`.**
   - `cubeDetail` (stored `Decision` column) and `detail` (app-level `Decision` TS field, recomputed at every read) are confirmed never rendered or consumed anywhere — only `myLabel`/`bestLabel` reach the UI.
   - Replace `cubeDetail` with a `CUBE`-kind-only pair, `cubeActionPlayed`/`cubeActionBest`, storing the same short labels `actionLabels()` already computes (e.g. `"doubled"`/`"double"`) as real ingest-time columns instead of read-time recomputation — the same move Step 1 already made for notation.
   - Rename `notationPlayed`/`notationBest` → `movePlayed`/`moveBest` for parallel naming across kinds (`move*` for `CHECKER`, `cubeAction*` for `CUBE`).
   - `RESIGNATION`-kind `myLabel`/`bestLabel` deliberately excluded from this — stays read-time-computed, no new columns (explicit scope decision, not an oversight).

**3. Redesign match score / Crawford state: move `Decision.matchScoreBlack`/`matchScoreWhite`/`crawfordState` to `Game`, keyed by `userId`.** This is the one item with a confirmed, already-live (if currently inert) data bug behind it, so it's the highest-priority item of the four:
   - Root cause: `metadata.scores.black`/`.white` are not literal board colors — `black` means "whoever made this specific decision," `white` means "their opponent" — confirmed via a symmetric cross-check in two real matches. Every `Decision.matchScoreBlack`/`matchScoreWhite` row today holds "whoever-decided's score"/"opponent's score," not a stable per-color value, even though the column names imply otherwise.
   - Separately, but likely fixable by the same redesign: `lib/ingest.ts`'s `Match.matchLength` is set unconditionally on every processed event (whichever is processed last wins) — confirmed wrong for **107 of 4,350 matches**, where it's stored `null` (money game) despite clear evidence of a real fixed length from other events in the same games.
   - Proposed shape: `Game.userScore`/`Game.opponentScore` (naming TBD), resolved via the same `me`/`opponentUserId` logic `lib/ingest.ts` already uses for `PlayerIdentity`, mirroring the existing `Match.userScore`/`opponentScore` precedent (that pair is the match's current/final score from `analyses/list`; the `Game`-level pair would be the score *entering that specific game*). `Game.crawfordState` moves alongside it — also a per-game fact. Source from the **first** event in the game by `eventId` (this project's established convention for other per-game facts, `plyNumber`/`playedAt`) — chosen because trusting "whichever event happens to be last" is the confirmed root cause of the `matchLength` bug, and a late-game value shift was observed in both real games checked (not fully explained, but avoided by sourcing from the first event). Apply the same "source from the first event, don't blindly overwrite" fix to `Match.matchLength` itself while doing this, since it's the identical bug pattern.
   - Blast radius today: confirmed `grep`-clean — neither `Match.matchLength` nor `Decision.matchScoreBlack`/`matchScoreWhite` is read anywhere outside the ingest writer and fake-data seed scripts. No live display bug, but real, confirmed-wrong data sitting in the table today, affecting 107 real matches' `matchLength` specifically.

**Suggested sequencing**: items 1 and 2 are straightforward schema cleanup (drop redundant/dead columns, add structured replacements, rename for consistency) — same shape of work as Steps 3-5's migrations, low risk, no live bug behind them. Item 3 is the one with a confirmed real (if dormant) correctness bug and new semantics to design carefully (the unexplained late-game value shift should probably be understood before finalizing the "first event" sourcing rule as permanent) — worth its own dedicated propose-then-implement pass rather than bundling with the others.

## New discrepancy found — `Match.matchLength` / `Decision.matchScoreBlack`/`White`/`crawfordState`

**This is the one real, newly-found problem from this pass**, and it's already live in production data, not hypothetical.

The existing doc claims: *"`metadata.scores` is `null` for money-game-type matches... confirmed against a real match: `scores: null` *and* `match_length: null` together, consistently across every decision in the match."* Re-checking this against match 34206386 (chosen specifically because our own DB had it flagged as a money-game example) found this is **false for this match**: its `move_commited` (`CHECKER`) events uniformly report `scores: null, match_length: null, crawford_state: "none"`, while its `dice_rolled` (`CUBE`-check) events in the **exact same games** uniformly report real values (`scores: {black: 4, white: 3}, match_length: 5, crawford_state: "post_crawford"`). Checked per-event-type across all 5 live files to confirm this isn't a general `move_commited`-is-always-null rule: the other 4 games' `move_commited` events are 100% non-null. The inconsistency is confined to specific matches (Galaxy-side, not ours) — not a universal pattern.

**This has already produced wrong stored data.** `lib/ingest.ts`'s `matchLength` variable is set unconditionally on every processed event (`matchLength = metadata.match_length;`, declared once per match, overwritten by whichever event is processed last) — so for an affected match, the final `Match.matchLength` value depends on which event type happens to be last in iteration order, not on the match's real length. Confirmed directly: match 34206386's stored `Match.matchLength` **is `null`** today, even though it's clearly a real fixed-length (5) match-play game (not money), per its own `CUBE`-kind decisions' `crawfordState`/`matchScoreBlack`/`White`.

**Measured scope**: 107 of 4,350 matches (2,490 of which are currently stored with `matchLength: null`) have at least one `Decision` row with real evidence (`crawfordState != 'none'` or a non-null `matchScoreBlack`) contradicting their own `Match.matchLength: null` — i.e., 107 real matches are currently mis-stored/mis-displayed as money games.

**Blast radius, assessed**: `matchLength`/`matchScoreBlack`/`White`/`crawfordState` are display/categorization fields — confirmed via `grep` they don't feed `MistakeStat`, `RepeatedPosition`, cube rendering, or PR calculation (those depend on `classification`/`kind`/`errorSeverity`/`rawError`, all independently verified correct above, unrelated to this). So this is real, confirmed, and already live — but in the lower-stakes tier the audit itself would flag, not the grading-logic tier. **Also confirmed currently dead data**: `grep` across the whole codebase shows neither `Match.matchLength` nor `Decision.matchScoreBlack`/`matchScoreWhite` is read anywhere outside `lib/ingest.ts` (the writer) and the fake-data seed scripts — no live display bug today, just incorrect data sitting unused. **Not fixed in this pass** — this was a re-verification task, not an implementation one.

### A second, deeper discrepancy found while discussing this one — `matchScoreBlack`/`matchScoreWhite` are mislabeled for *every* row, not just the 107

Investigating *why* match 34206386's score looked internally contradictory (its own `dice_rolled` events disagreed with each other depending on which player's cube-check it was) led to the real explanation, confirmed by the user and then verified rigorously with a symmetric cross-check across two real matches: **`metadata.scores.black`/`.white` are not literal board colors at all** — `black` means "whoever made *this specific* decision," `white` means "their opponent," regardless of which real color that player is playing as that game. Verified by checking that user A's own reported "black" value exactly equals user B's reported "white" value for A, and vice versa, in both match 34206386 and match 46797221 (an earlier, less careful check of 46797221 had looked consistent with literal colors only by coincidence — that player's real color happened to match the "mine" label).

This means `Decision.matchScoreBlack`/`matchScoreWhite`, as currently stored (`lib/ingest.ts`: `metadata.scores?.black`, `metadata.scores?.white`, verbatim), hold "whoever-decided's score" / "opponent's score" on every single row — not a stable, row-independent "the black player's score." Still confirmed dead data (nothing reads it today), so no live bug, but the column names are actively misleading for when something eventually does.

**One remaining open question, not yet resolved**: even under the corrected "mine/opponent" reading, one player's own score value wasn't perfectly constant through either of the two full games checked — it shifted once, late in the game, right around the cube action in both cases. Not yet explained (possibly a projected/hypothetical value specific to cube-decision context, not investigated further this pass).

**Proposed redesign (not implemented — noted for a future pass)**: move score and Crawford state off `Decision` entirely and onto `Game`, tied to `userId` instead of `black`/`white`:
- `Game.userScore`/`Game.opponentScore` (naming TBD) — resolved via the same `me`/`opponentUserId` logic `lib/ingest.ts` already uses for `PlayerIdentity`, computed once per game instead of duplicated/ambiguous per decision. Mirrors the precedent `Match.userScore`/`opponentScore` already set (those come from the separate `analyses/list` endpoint and represent the match's current/final score; the `Game`-level pair would represent the score *entering that specific game*).
- `Game.crawfordState` moves alongside it — same reasoning, a per-game fact (doesn't change mid-game), not a per-decision one.
- Sourced from the **first** event in the game by `eventId`, matching this project's established "first, not last" convention for other per-game facts (`plyNumber`, `playedAt`) — chosen specifically because the late-game shift means trusting "whichever event happens to be processed" isn't safe, and the first event is the one point most likely to reflect the game's true starting state rather than an in-game projection.
- `Decision.matchScoreBlack`/`matchScoreWhite`/`crawfordState` would be dropped once replaced (confirmed no current readers, so no migration-compatibility concern beyond the schema change itself).
