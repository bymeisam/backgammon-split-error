# Forum text posts + board handoff — design proposal

**Scope:** implementation direction for the approved text-only forum flow and board handoff. The queue decisions are authoritative: posts may have no board; `/forum/new` is title/body plus two “Add a board…” actions; at most one board; no raw IDs or source selector; sessionStorage carries one board under one key and navigates to plain `/forum/new`; no topics, categories, or reply boards. This proposes presentation only; it does not change app code.

## Recommendation

Keep the existing calm, medium-width forum shell and familiar title/body form, but make the board an optional, visually subordinate attachment—not a required form section. Use the shared `PageShell`, `Card`, and `Button`; retain theme tokens and page-local styles in the route’s `*.styles.ts`. Board actions should be contextual to the board and visually secondary. Do not add severity colour, new tokens, a new font, or a new form-card look.

### `/forum/new`: empty and attached states

- **Empty:** page title and breadcrumbs as today. A single column, same left alignment and medium width as other forum pages. Title input then a generously tall, full-width body textarea; labels remain visible. Follow with a small “Board (optional)” section containing two adjacent-on-wide / stacked-on-phone secondary buttons: **Add a board from a match** and **Add a board from the position builder**. Keep a short helper line that a post can be published without a board. The form actions follow: primary **Post**, secondary **Cancel**. No board placeholder card is needed; avoid a second visual box around an empty attachment.
- **Attached:** retain title/body first, then one compact board attachment panel below them. Show the board at responsive width with only useful context/caption, not internal IDs or a source selector. Put **Remove board** as a quiet, keyboard-accessible text action in the attachment header; after removal, return to the same empty optional-board controls. One attached board only. No add-another affordance.
- **Session handoff states:** an absent key is the ordinary text-only empty state, not an error and not a blocker. A valid payload renders the attached-board state. If a present payload is malformed, unsupported, or unavailable, render the empty form without exposing raw data and give a concise, non-blocking inline message such as “The board couldn’t be attached. You can still post without one.” Text entry and submit must remain usable. Keep this feedback near the optional-board controls, not as a modal or full-page error. A successful board return must not alter the plain `/forum/new` URL or leak IDs into visible content.

### Contextual “Post to forum” action

Offer the same concise label and secondary Button treatment at every requested viewable board: replay, position builder, match analysis, mistakes, and repeated positions. Place it immediately below or in the existing control row immediately below the board—not in a distant page header—so the action clearly applies to the displayed position. Keep it near existing board controls and metadata without obscuring the board, move list, or figures. At narrow widths it may wrap to a new line, but must remain visible without horizontal scrolling or covering the board. Where several boards can be navigated (replay/mistakes/repeated positions), the handoff must refer to the currently selected board. Respect the existing write-gate visibility convention. Use one shared action/flow if implementation already has a shared board-action seam; otherwise keep wrappers page-local rather than introducing a styling abstraction solely for visual uniformity.

### Text-only forum list, post, and edit

Keep the current scannable list cards and title-first hierarchy. Update metadata so a zero-board post reads naturally; retain established author/date/reply metadata if replies remain part of the surrounding forum. Board count should only appear when useful. Detail and edit pages should present title/body as the post’s content and retain existing edit/save/cancel conventions. Remove board, engine-analysis, and move/reply-proposal UI from this feature’s post/list/edit flow as specified—do not replace it with tabs, empty panels, or disabled placeholders. Do not remove existing reply functionality unless the approved implementation scope explicitly says to; the queue rules out reply boards/proposals, not necessarily ordinary replies. Preserve meaningful empty-list and posting-disabled states.

## Responsive and accessibility requirements

- Use the established PageShell breakpoints and max-width: the 390px form should use the available content width; at desktop keep the text measure comfortable rather than stretching fields across the full board workspace. Keep labels above controls and maintain current vertical rhythm.
- Target at least 44px touch height for the two board-source actions and Remove, even though compact shared buttons are smaller. Use an existing suitable Button size plus a page-local sizing class where needed; do not invent a control style. Make the two sources explicit in visible text, not icons alone.
- Use associated labels for title/body and a semantic heading for the optional board section. Give the board a concise accessible description/caption. Removal must be a real button with an accessible name that identifies the action; do not make a tiny unlabeled icon the only control.
- Retain visible keyboard focus through the shared focus primitives. Ensure board controls and submit/cancel can be reached in logical DOM order; source actions, remove action, and submit should not rely on hover. Announce attachment/removal and malformed-handoff feedback accessibly (e.g. polite status for attachment changes; alert only for a meaningful failure), without stealing focus.
- The colour theme tokens already change for light/dark. Keep input, button and helper text on their established surfaces; do not use `ink-faint` on sunken surfaces. No new colour coding is needed. I did not calculate contrast ratios; use the shared theme tokens and existing contrast rules rather than choosing new shades.

The available screenshots are **2026-10-14 review-refinement-7**, at 390px and 1280px, and show the current multi-position/source-ID/analysis/reply implementation—not the approved target. They are useful for shell, board scale, and existing theme behavior only; do not treat those old controls or content as requirements.

In the target, removing that required-position form block leaves a long gap unless the two source actions sit immediately after the body; the optional empty state should feel intentional rather than missing content. Current markup/style anchors: `app/forum/new/NewPostForm.tsx:127-210`, `app/forum/forum.styles.ts:22-52`.
- `forum-write-new-decision-1149340--1280-light--full.png` shows a board preview nested in the attachment card; `forum-write-position-builder--1280-light--full.png` shows the large board with the existing full-width primary “Post to forum” at the bottom of the controls column. The approved contextual action should retain board association but should not visually compete with primary page actions. Existing builder placement is visible at `app/position-builder/PositionBuilder.tsx:119-131` and in the screenshot; its responsive layout is `app/position-builder/positionBuilder.styles.ts:4-16`.
- The form already uses shared Button and an available removable-position pattern (`app/forum/new/NewPostForm.tsx:127-137,208-220`), while its styles point at `shared.input` and use route-local layout (`app/forum/forum.styles.ts:22-29`). Preserve these conventions but simplify to one attachment.
- Replay currently places a small secondary “Post to forum” beside the stepper end (`app/matches/[matchId]/replay/[gameIndex]/GameReplay.tsx:188-215`); this is a good starting pattern for compact contextual placement, but the action must remain reachable when narrow layouts wrap.
- Screenshot `forum-write-list--390-light--full.png` shows title-led cards with author/date/replies/position counts. With zero-board posts, position count must not suggest an attachment is mandatory; preserve useful existing reply metadata if ordinary replies remain in scope. Current list rendering: `app/forum/page.tsx:32-50`.
- Existing light/dark screenshots show readable text and control outlines for the current form, but they do not verify future empty, attached, malformed-handoff, removal, submit/error, or 44px-target states. Do not claim those states are visually validated until captured.

## Implementation handoff

Suggested scope slices: (1) simplify `/forum/new` and edit/detail/list presentation to the text-only, zero-or-one-board model; (2) add the two source actions and valid/absent/malformed handoff feedback; (3) place the same contextual board action on each required board view. Follow the approved queue payload shapes without surfacing identifiers: `{ match: { decisionId } }` or `{ manual: { positionId, gnuMatchId, kind } }`. Keep styling in `app/forum/forum.styles.ts` for page-local forum styles and in each board page/component’s colocated `.styles.ts` for its own placement, using shared UI primitives. Capture 390px and desktop screenshots in both light and dark after implementation; explicitly inspect attached and removed board, malformed/absent handoff, and all five board-action entry points.
