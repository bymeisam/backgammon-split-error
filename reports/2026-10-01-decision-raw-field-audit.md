# Audit: what this app reads out of `Decision.raw` (and other raw/JSON fields)

Read-only investigation, no schema or code changes made. Goal: a single canonical reference of every distinct piece of data this app depends on from Galaxy's raw JSON payload — where it's extracted, how it's used, whether it already has a dedicated column, and whether it's reliable — so a follow-up task can decide which of these should become real columns, and in what order.

Built from three parallel investigations: (1) the Prisma schema + `lib/ingest.ts`'s ingest-time extraction (ground truth for what's already a column), (2) `lib/mistakes.ts`/`lib/decisionFromRow.ts`/`lib/cubeState.ts`'s read-time extraction (the bulk of the app's actual raw-JSON dependency), (3) everywhere else — `scripts/`, `app/api/`, `lib/recompute-*.ts`, raw SQL. Two claims below were independently re-verified directly, not just trusted from agent output: that `sourcePositionId` is genuinely not a `Decision` column (checked the full schema field list and all 11 migrations), and that `notationPlayed`/`notationBest` are stored but never actually read by any current query path (checked `DecisionRow`'s type and `DECISION_LIST_SELECT` directly).

`Decision.raw` is the only column anywhere in the schema storing a raw Galaxy event payload (`SyncRun.errors` is the only other `Json` column, and it's this app's own sync-error log, unrelated to Galaxy data).

## Cross-cutting findings (not single fields, but real inconsistencies worth knowing about)

1. **Severity disagreement between the two read paths.** `extractDecisions` (live-fetch: `/matches`, `/galaxy/matches`) computes severity itself — a local `absError >= 0.08` threshold — and never reads `errorSeverity` at all. `decisionFromRow`/`decisionFromRowForReplay` (DB-row: replay, `/mistakes`) instead read the dedicated `errorSeverity` column (Galaxy's own `DOUBTFUL`/`ERROR`/`BLUNDER` classification). These can disagree on whether the *same real decision* is a "blunder" depending on which page you view it from. Not a column problem (the column already exists and is correct) — a logic-consistency question for a follow-up to decide deliberately, not a schema change.
2. **Three different null-`rawError` behaviors** across `extractDecisions` (excludes entirely), `decisionFromRow` (drops the row), `decisionFromRowForReplay` (treats as `absError: 0`, keeps the row) — each deliberate for its own view's purpose, but worth knowing they're not unified.
3. **`kind`/`countAsDecision` are re-derived from raw in the live-fetch path but read from columns in the DB-row path** — same real values today (both trace back to the same ingest), but it's duplicate logic in two places that could silently drift if either side changes independently.
4. **`notationPlayed`/`notationBest` columns are populated at ingest and then never read** — confirmed directly, not just reported by an agent. This is the one item in this whole audit fixable with *zero* schema change — just start selecting and reading the columns that already exist, in `lib/decisionFromRow.ts` and `lib/decisionQueries.ts`.
5. **The two real "unindexed JSON access is slow" precedents live only in code comments, not in `docs/field-mapping.md`.** `lib/decisionQueries.ts`'s `findPositionOccurrences` (`FORCE INDEX`, 11.4s→1.2s) and `lib/recompute-repeated-positions.ts` (dropped `GROUP BY`, 341s→~2s) are both real, measured incidents — exactly the evidence this audit's performance heuristic leans on — but aren't captured anywhere a future reader would find them without reading those two files' comments directly.

## Per-field recommendation (no dedicated column today)

| Field | Performance heuristic | Portability heuristic | Verdict |
|---|---|---|---|
| **`sourcePositionId`** | **Strong yes** — two independent, measured slow-query incidents (341s and 11.4s) from the exact same unindexed JSON path, both only worked around (dropped `GROUP BY`, `FORCE INDEX`), never actually fixed at the index level | **Strong yes** — "which board position was this decision made at" is a core domain fact (GNU Position ID is itself a storage-neutral standard, not Galaxy-specific) any future source would need to supply | **Both agree — top candidate.** A column with this exact name/purpose/collation already exists as precedent on `RepeatedPosition`; adding the equivalent to `Decision` is the most scoped, lowest-ambiguity change in this list |
| **Dice roll** | Moderate — never directly queried/filtered/sorted on today, but the backward-scan requires over-fetching sibling `countAsDecision: false` rows on every call site just to make the lookup possible (`loadDecisionItems`'s "second unfiltered query" exists partly for this) | **Yes** — "what did this player roll" is a basic, universal fact; today it's entirely dependent on Galaxy's specific event-shape convention (checker moves never carrying their own roll) via a backward scan that a future data source would have to replicate exactly or this breaks | Both lean yes, performance case weaker than `sourcePositionId`'s proven pain. Natural to compute once at ingest time (same shape as `plyNumber`/`cubeOwnerUserId` already do) rather than re-scanned on every read |
| **Cumulative cube value (not just owner)** | **Low** — display-only today, nothing filters/sorts/queries on it | **Moderate-to-high** — the full value-and-owner-at-this-decision state requires walking the entire game's event history under a nontrivial state machine (now encoded once in `lib/cubeState.ts`); a future source would need to supply this or the app re-implements the walk against a differently-shaped stream | **Flagged disagreement** (low urgency by the performance heuristic, real value by the portability one) — but cheap to resolve: `cubeOwnerUserId`'s ingest-time walk already does ~90% of this work (same event loop, same state machine shape), so adding a parallel value tracker to that existing walk is a small extension, not new infrastructure |
| **`myLabel`/`bestLabel`/`detail` (display text)** | No | **Low** — these are presentation-layer English strings, not a structured fact a future source needs to supply in this exact form; the underlying structured facts they're built from (`double`/`take`, `should_resign`, notations) are either already columns or are the next item below | **Both say low priority** — recommend leaving as read-time-derived text. The *productive* fix here isn't a new column, it's reading the `notationPlayed`/`notationBest` columns that already exist instead of re-parsing raw for the notation half of this |
| **`review.double`/`review.take` (raw booleans)** | No — not queried on | Moderate — currently the only durable record of "did a double/take actually happen on this row" is the lossy `cubeDetail` *string*; a future source supplying structured cube actions differently would have nothing better to map onto | Portability edges out slightly, but low overall priority — mostly superseded in importance by the cube-value item above, which already implies capturing this |

No disagreement found in the opposite direction (high-performance-urgency but low-portability-importance) — every field that showed real, measured query/filter pain (`sourcePositionId`) also independently reads as a genuine cross-source domain dependency, not a Galaxy-specific implementation artifact.

## Explicitly out of scope for this pass

No schema changes, no code changes, no migrations. This is the inventory + recommendation; a follow-up task decides which of these to actually build and in what order.
