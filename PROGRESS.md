- Fixed a bug in the fixed-perspective toggle (above) found right after shipping: move arrows rendered incorrectly for opponent decisions when the toggle was on. Root-caused before fixing, per request:
  - `Board.tsx`'s `moveAnchor()` — the function that converts a sub-move's `from`/`to` point refs into pixel anchors for the arrow — hardcoded `decoded.mine`/`decoded.mineBar`/`decoded.mineOff` (and the bottom-half bar/off-tray geometry constants that go with "mine") regardless of whether the board was being rendered flipped. That assumption ("the mover is always on the `mine` side") holds pre-flip (GNU position IDs are always decoded from the on-roll player's own perspective) but is exactly what `flipPerspective` inverts for an opponent decision — post-flip, the mover's checkers live in `decoded.opponent`, not `decoded.mine`. `decoded`/`subMoves` arriving in `Board.tsx` were already correctly transformed upstream (`BoardPanel.tsx`'s `flipPerspective`/`mirrorSubMoves`); only the arrow-anchoring code itself had the stale assumption.
  - Confirmed with real data before fixing anything: decision `2524` (match `977248` game `4`, `8/7* 7/5 6/5`) — point case: arrow read `decoded.mine[16] = 0` instead of the correct `decoded.opponent[16] = 3` for its origin's stack height (column/point itself was unaffected — only the vertical anchor within it). Decision `2540` (`Bar/23 13/11(3)`, same game) — bar case: anchored at the bottom-half ("mine") bar position regardless of flip, while the actual checker is drawn in the top half (`decoded.opponentBar`) once flipped — a wrong board *half*, not just a wrong offset. Decision `672276` (match `33425869` game `1`, `7/3(3) 4/off`) — same root cause for the off-tray case, found via a DB search for a genuine opponent bear-off decision (none existed in game 4 of 977248 itself).
